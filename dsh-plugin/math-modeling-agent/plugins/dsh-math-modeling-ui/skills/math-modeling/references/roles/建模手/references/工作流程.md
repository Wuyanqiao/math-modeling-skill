# 建模手工作流程

> 共享运行时、当前 profile、用户要求和已核验规则优先；以下高级工具步骤仅在依赖/授权具备且任务需要时加载。缺能力时保留可验证产物并报告审查等级，数量建议不阻断。
## 一、读题与附件

1. 枚举题目、附件、数据表、图片和模板，记录文件哈希或明确版本。
2. 按子问题列出目标、约束、输入、输出和评价口径。
3. 检查数据字段、单位、缺失、异常、重复、时间顺序和空间关系。
4. 无法确认的事实写成待确认项，不自行补造。

## 二、理解后形成结论目标

先回答“题目要求最终说明什么”，再讨论模型。结论目标应描述输出类型和评价标准，不预写数值结果。

示例：

- 输出满足全部容量与时间窗约束的配送方案，并比较成本和稳定性。
- 输出未来各期预测及其不确定性，并用留出数据检验误差。

## 三、选择模型

每个子问题先选择可靠基线，再按证据价值和预算增加模型，没有通用数量上限。模型数量包括主模型、并行对比模型或机理不同的串联阶段模型；灵敏度分析和误差检验不计作独立模型。

物理建模按“模型族”计数：若两光束干涉与多光束干涉共享同一物理机制和核心变量，只是反射阶次或精度不同，应视为同一模型族的基础版与扩展版。只有控制机理、状态变量、边界条件体系或求解目标发生实质变化时，才另计一个模型。

选择时逐项核对：

- 是否表达题目中的关键结构和约束。
- 数据是否满足模型假设。
- 是否能由 Python 或 MATLAB 可靠实现。
- 是否有清晰的验证方案。
- 创新是否来自题目结构、特征、约束、算法或验证，而非简单改名。

避免直接套用常见简单模型冒充创新；模型选择以问题适配、可验证和可实现为准。

## 四、搜索理论依据

按需读取 `../../../../tools/paper_search/SKILL.md`，选择可用检索源并记录服务状态；DOI/题名匹配仅代表元数据匹配，引用前核验原文与主张。

## 五、写交付物

先按 `references/前置合同.md` 的八项表格（任务定义、数据、结论类型、模型、数学定义、实现、验证、风险）形成模型合同，作为 `题目分析报告.md` 的骨架；合同不是独立交付物。

### `题目分析报告.md`

至少包括：

1. 题目与附件清单
2. 子问题拆解
3. 数据理解与预处理计划
4. 假设及依据——**关键假设 vs 可放宽假设分级**：标出每条假设是"关键"（放宽会导致模型失效）还是"可放宽"（放宽只影响精度），并说明放宽后的复验方式（如灵敏度分析、参数扫描）。关键假设通常 ≤3 条，全部可放宽假设合计 ≤7 条；假设必须有依据（题目数据、领域文献或官方规则），不能凭空设定。
5. 每题模型与数学定义
6. 算法步骤、输入输出和验证方式
7. 编程依赖和候选图表
8. 风险与回退条件
9. 文献依据

### `术语表格.md`

至少包括中文术语、英文术语、符号、定义、单位、首次出现位置和禁止混用的近义词。

符号栏遵循以下规范：

- 只登记跨公式或章节复用的全局符号；求和哑指标或单个推导中的临时量在公式附近定义。
- 符号使用可渲染的标准数学格式（Markdown 行内公式 / Word 原生 OMML / LaTeX 数学模式）；最终论文不得显示 `x_ij`、`alpha`、`C_total`、下划线、反斜杠或公式定界符等源码。
- 遵循领域惯例：变量用数学斜体，向量用粗体小写，矩阵用粗体大写，集合用花体或约定的大写字母，函数名和说明性下标用正体。
- 一符一义；需要区分对象、时间或情景时使用实际排版的上下标，不用可见下划线拼接名称。
- 单位采用统一的标准写法；没有单位时写“无量纲”。
- 论文的符号说明表从本表提取“符号、含义、单位”三列，不另建第二份符号定义。

## 六、M1 独立验收

两个文件完成作者自检后立即冻结输入快照，并按 `../../../../references/Subagent调度.md` 派发未参与编写的质检 Subagent。严格模式下 `M1` 未返回 `PASS` 时不得进入编程；质检发现问题后由建模手修正，产物变化会使原回执失效，必须复验。

## 七、反馈修正

编程手返回实现证据后，直接修订上述两个文件并说明变更，不创建同义版本文件。
